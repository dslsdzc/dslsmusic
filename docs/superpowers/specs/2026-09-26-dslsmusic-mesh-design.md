# dslsmusic 远程控制与个人音乐网格 设计文档

- 日期：2026-09-26
- 状态：草案，未定项见 §8
- 关系：本文档独立于 v1 设计文档（`2026-09-26-dslsmusic-design.md`），因为它定义的是一个**独立子系统**，有自己的里程碑与风险

---

## 1. 这是什么

**不是「加一个遥控功能」，是把你所有设备连成一个个人音乐网格。**

用户的原话是「手机控制电脑、电脑控制手机，局域网自动扫描，不是局域网走 P2P」，随后补充「数据库可以共享，比如电脑有 GPU 跑 AI 更快就交给电脑跑」。

合起来是四层能力：

| 层 | 内容 |
|---|---|
| **遥控** | 双向：任一设备可控制任一设备正在播放的内容 |
| **媒体中继** | 远端显示完整界面（封面/逐字歌词/队列），媒体数据由**播放端中继**，远端不直连网易云 |
| **共享** | 各端**本地完整可用**，联网时同步 |
| **计算卸载** | 节点声明能力，重任务（音频分析）由**最合适的节点认领** |

---

## 2. 为什么它契合现有架构

v1 的核心设计（§2.1）是**单向数据流**：

```
UI ──dispatch(action)──▶ core ──处理──▶ 状态快照 ──▶ UI 渲染
```

**远端设备就是「另一个 UI」。** 它 dispatch 同一套 action、渲染同一份状态快照——**不需要为它改 UI 层，也不需要为它改 core**。

```
        ┌──────── 本机 UI ────────┐
        │                         │
core ───┼──────── 远端 UI ────────┤   ← 同一个 action/state 边界
        │                         │
        └──────── 未来的 Web/CLI ─┘
```

而 v1 §4.1 早就预留了「同一个 core 再包一层可选的 axum server」。

> **所以真正要造的不是「遥控」，是「把这个已有的边界搬到线上」**——序列化、传输、配对。
> 这比「从零做遥控」小得多。

**但要付的代价**：那个边界当前是**进程内类型**，要变成**可序列化的线格式**。这意味着 `Action` / `StateSnapshot` 的所有类型都要 `serde`，而且**快照必须自足到能让另一台设备渲染出界面**（这是个设计约束，见 §8）。

## 3. 四层能力的设计

### 3.1 发现与配对

**发现（局域网）**：mDNS/DNS-SD 广播 `_dslsmusic._tcp.local`。

**发现（跨网）**：不是「扫描」，而是**已知身份直连**——`iroh` 用公钥拨号，打洞失败自动走中继。

> ⚠️ **发现 ≠ 信任。** mDNS 是**无认证**的，局域网里任何人都能广播同名服务。
> **「扫到了」绝不能等于「可以控制」。**

**配对是强制的，而且我们已有现成模式**：v1 §4.4 的网易云二维码登录。手机扫电脑的码 → 建立信任 → 之后才可控制。

技术上是 `spake2`（PAKE，口令认证密钥交换）——**扫码传递的是短期口令，密钥交换本身不依赖信道安全**，所以中间人也无法从扫码过程中推导出会话密钥。

### 3.2 遥控

命令与状态**共用同一条通道**：

```
远端 ──Action──▶ 播放端 core ──▶ StateSnapshot ──▶ 所有已配对设备
```

**关键设计：状态快照是广播的，不是查询的。** 否则 N 个遥控端会各自轮询，且不同端看到的进度会不一致。

**命令类型**：播放/暂停/上一首/下一首/seek/音量/播放模式/队列增删改/音质切换/响度开关/…——**就是本机 UI 能做的那些，一一对应**。

**不做的事**：远端不能做本机 UI 做不到的事。这条约束让权限模型天然收敛——**不存在「遥控专用后门」**。

### 3.3 媒体中继

远端要显示封面、逐字歌词、队列，而**远端不登录网易云**（避免 §4.4 的封号风险，也让本地音乐可用）。

所以媒体数据由**播放端中继**：

| 数据 | 来源 | 缓存策略 |
|---|---|---|
| 封面 | 播放端已缓存 | 按尺寸分档，远端本地缓存 |
| 歌词 | 播放端已解析 | 文本很小，直接传 |
| 音频 | 播放端在播 | **不传给遥控端**（遥控端不出声） |

> **「音频不传」是遥控模式的定义。** 若将来要做同步播放（两端都出声），音频就必须传——那是另一个量级的工程（时钟同步、抖动缓冲），**不在本文档范围**。

### 3.4 共享（本地优先 + 同步）

**每台设备都有完整的本地数据库，离线完全可用；联网时互相同步。**

同步的内容：

| 类别 | 冲突可能 | 备注 |
|---|---|---|
| 收藏 / 歌单 | **有**（两端同时改同一个歌单） | 需要冲突解决策略 |
| 播放历史 | 低（追加为主） | 合并即可 |
| **分析结果缓存** | 无（同一首歌的结果应当一致） | **纯收益，可自由合并** |
| 音频文件缓存 | 无（内容寻址） | 按 hash 去重 |
| 本地库索引 | **不应同步** | 各设备的本地文件本来就不同 |

> ⚠️ **同步是本设计里最容易出错的部分。** 冲突解决策略见 §8 未定项——
> 「两端同时改了同一个歌单」没有显然正确的答案。

### 3.5 计算卸载

**这是本设计里最新颖、也最直接解决实际问题的一层。**

v1 §18.3 标过一个约束：**用户的开发机是 4 核 A8-7650K，实测负载已 5.74、quickshell 占 48% CPU**，所以「分析任务必须让路给音频线程」。而分析是重活（tempogram + chroma + ML 推理）。

卸载把它变成**分布式任务队列**：

```
任务入队（来源：任意设备发现一首没分析过的歌）
      ↓
节点广播能力（有无 GPU / 核数 / 当前负载 / 是否充电 / 是否在播放）
      ↓
最合适的节点认领（租约）
      ↓
结果写回共享缓存 → 所有设备直接受益
```

**这和「共享」天然咬合**：分析结果本来就该是共享的——**一首歌分析一次，所有设备都受益**。

#### ⚠️ 但有一条硬约束：卸载要搬运音频

分析需要音频样本，而音频在**播放它的那台机器**上。三条路：

| 方式 | 代价 |
|---|---|
| 把音频传给分析方 | 一首无损 ~30MB。**局域网千兆 ~0.3 秒，划算；跨网 P2P 就未必**（分析本身也就几秒到几十秒） |
| 分析方自己取 | 需要共享登录态 → §4.4 的封号风险 + 安全风险 |
| **分析方已有该文件/缓存** | **零搬运**——但这要求音频缓存也共享（见 §3.4） |

> **判据（未定项）**：跨网卸载必须按 `预估分析耗时 > 传输耗时 × 权重` 实时判断，
> 而不是无条件卸载。局域网则可以直接卸载。

**另一条必须守住的**：认领任务的弱机器**仍然要让路给音频线程**（v1 §16.2 的
「xrun 必须为 0」是硬指标，不因为任务来自别人而放松）。

## 4. 技术选型

| 需求 | 选择 | 许可 | 理由 |
|---|---|---|---|
| 局域网发现 | `mdns-sd` 0.21 | Apache-2.0 OR MIT ✅ | 无 async runtime 依赖 |
| P2P + 打洞 + 中继兜底 | **`iroh` 1.2** | MIT OR Apache-2.0 ✅ | 「用公钥拨号的 p2p QUIC 连接」，**自带中继兜底，不用自建 STUN/TURN**。12586★，活跃 |
| 配对密钥交换 | `spake2` 0.4 | MIT OR Apache-2.0 ✅ | PAKE，扫码可安全引导 |
| 线格式 | `serde` + `postcard`（或 `bincode`） | — | 待定，见 §8 |
| 本地存储 | 沿用 v1 §10 的 SQLite | — | 加一层同步 |

**许可全部干净**，且都兼容 GPLv3（v1 §14.1）。

## 5. 安全模型

| 项 | 设计 |
|---|---|
| **身份** | 每台设备一对长期公钥（`iroh` 原生按公钥拨号） |
| **配对** | 强制、显式（扫码 + PAKE）。**未配对设备即使被发现也不能发命令** |
| **权限粒度** | 待定（见 §8）。当前最小可用：**配对 = 完整的播放控制权 + 只读的状态订阅** |
| **撤销** | 必须能单方面解除配对，并让对端立即失效 |
| **传输** | `iroh` 自带 QUIC + TLS，链路加密由它保证 |

> ⚠️ **「未配对设备即使被发现也不能发命令」是硬约束。** 局域网里任何人都能
> 广播 mDNS 服务，若把「发现」当作「可信」，等于把播放控制权开放给同网段所有人。

## 6. 对现有设计的影响

| v1 文档位置 | 影响 |
|---|---|
| §2.1 边界铁律 | `Action` / `StateSnapshot` 需要 **serde 化**；这是本设计的前置条件 |
| §4.1 「可选的 axum server」 | **这条从「可选」升级为「必要基础」**——它是网格的入口 |
| §4.4 登录只读约束 | **中继模式让它更容易守**：远端不需要登录，只连播放端 |
| §10 数据与缓存 | **改动最大**：SQLite 之上要加同步层 |
| §16.2 音频优先 | **重要性上升**：弱机器可能同时在跑别人派的分析任务 |
| §18.3 分析管线 | **从「本机后台任务」变成「分布式任务队列」** |
| §18.3 的「分析必须让路给音频」 | 依旧成立，且现在还要加「让路给本机 UI」 |

## 7. 里程碑草案

**待定**——本文档先定架构与选型，里程碑等 §8 的未定项收敛后再排。

一个初步的顺序直觉：

```
M1  单机仍是单机，但把 Action/State 做成 serde 化的（前置，不影响现有功能）
M2  局域网发现 + 配对 + 遥控（单向即可验证）
M3  媒体中继（远端能显示完整界面）
M4  双向（对等化）+ 断线重连
M5  跨网 P2P（iroh）
M6  共享同步（最难，冲突模型要先定）
M7  计算卸载（依赖 M6 的缓存共享）
```

## 8. 未定项

| # | 未定项 | 为什么重要 |
|---|---|---|
| 1 | **冲突解决策略** | 集合数据（歌单/收藏）在两端并发修改时无显然正确答案。候选：CRDT / LWW-per-field / 操作日志重放。**这是 §3.4 最大的技术风险** |
| 2 | **状态快照的边界** | 快照要自足到能让远端渲染界面。含多少？队列全量？封面 URL 还是内联？**这决定协议带宽** |
| 3 | **权限粒度** | 配对后是「全部控制」还是可分权（只读 / 可控制 / 可管理）？ |
| 4 | **跨网卸载判据** | §3.5 的 `耗时 > 传输 × 权重` 里，权重怎么定？局域网是否一律卸载？ |
| 5 | **线格式** | `postcard`（紧凑、no_std 友好）vs `bincode` vs `serde_json`（可调试）。协议要长期兼容，**格式选定后改成本高** |
| 6 | **协议版本兼容** | 不同版本的客户端之间怎么握手？网格里可能同时有新旧版本 |
| 7 | **设备身份恢复** | 公钥丢了（重装系统）怎么办？重新配对？ |
| 8 | **任务租约超时** | 认领任务的节点离线，任务怎么回收？超时判定多长？ |

## 9. 风险

| 风险 | 说明 |
|---|---|
| **同步是分布式系统最难的部分** | §3.4 是本设计里唯一「做错了会丢用户数据」的地方。其余各层错了只是功能不可用 |
| **`iroh` 生态较新** | 1.x 但属于新兴项目。缓解：把它的调用包在 trait 后面（沿用 v1 `platform/` 的做法） |
| **安全面扩大** | v1 是单机程序，没有攻击面。接入网络后**配对、撤销、权限**三处都必须做对 |
| **弱机器的双重压力** | 它既要播音频，又可能被派活。§16.2 的优先级规则要扩展到「网格任务 < 本机音频」 |
| **范围蔓延** | 「同步」很容易从「歌单对齐」滑向「完整的多端状态复制」。**必须严守 §3.4 那张表的边界** |
