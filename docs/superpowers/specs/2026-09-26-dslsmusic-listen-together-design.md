# dslsmusic 一起听 设计文档

- 日期：2026-09-26
- 状态：草案，未定项见 §9
- 关系：独立于 v1 设计文档与网格文档。它复用网格的 P2P 栈，但**不是**网格的一部分——网格是「你自己的设备之间」，一起听是「不同的人之间」。

---

## 1. 这是什么 / 为什么单独立一份

用户要一起听，且**两种后端都要**：走网易云官方的，和走我们自己 P2P 的。

一开始我把它当成「网格的同步播放」——但那是错的，有两条硬区别：

| | 网格 | 一起听 |
|---|---|---|
| 参与者 | **你自己的**多台设备 | **不同的人** |
| 出声 | 同一时刻只有一台 | **两端同时出声** |

而且调研推翻了网格文档里一条论断（见 §2）。

---

## 2. ⚠️ 先更正一处既有错误

网格文档 §3.3 写着：

> 「若将来要做同步播放（两端都出声），音频就必须传——那是另一个量级的工程（时钟同步、抖动缓冲）」

**这句话是错的**，至少对一起听是错的。

**已核实**：每一条会出声的实现都是**自己拉自己的流**——
`s12mmm3/QListenTogether`（`Main.qml:214` 调 `song_url_v1`）、`youshen2/MeloX`（`PlayerStore.swift:432` 打 `/api/song/enhance/player/url/v1`）。
`NeteaseListenTogetherAPI.swift` **全文没有任何房间音频/中继端点**。

**所以音频不必传——要同步的是时间线。** 那一整句「另一个量级的工程」的推理起点就是假的。
（它只在「一端持有本地文件、另一端没有」时成立。）

> **但这不代表它便宜。** 取代「音频传输」的是一个同等分量的东西：
> **两端各自取流 ⇒ 队列里只能放两端都能取到的歌**，且**时钟必须我们自己造**（见 §5）。

## 3. 双人版与多人版：**是同一个功能的两次版本，不是两个功能**

用户提到「有多人版和双人版」。核实后：

- **2020-07-10 上线，双人**（官方公告 + 界面新闻同日报道）
- **2023-10 下旬「多人一起听」升级**
- **2023-11-16 官方原话**：「由**双人一起听升级到多人一起听**，突破房间人数限制」

**⇒ 建模为「一个功能 + 一个成员数」，不是两套设计。**

**人数上限：无定论，本设计不承诺。** 官方说「突破人数限制」但**没给数字**；云信文档说 2；专利实施例 10；活动文案提到「和 3 位好友组队」（=4）。
⚠️ 且 9 个 HTTP 接口里**没有任何一个带人数参数**——**人数大概率是服务端策略，不在客户端协议里**。
**⇒ 不要把人数当协议常量；UI 上不做承诺。**

## 4. 两个后端

### 4.1 共同部分（**两个后端都要自己实现**）

**这是本设计最重要的一条结论：即使是网易云后端，同步层也得我们自己写。**

```
共享队列 + 时间线（歌曲、起始位置、起始时刻）+ 控制权
                    ↓
        两端**各自**从音源取流 → 各自出声
```

**不传音频、不传音源凭证。** 每一端用自己的账号、按自己的音质设置取流。

### 4.2 网易云后端 —— 比预想的弱得多

**它拿不到实时下行。** 真实下行是**私有的 NIM（网易云信 IM）通道**，不是 HTTP：

- `TinyCloudMusic`（唯一复现真实通道的实现）：`/api/middle/im/token/get`，**`bizName=music_listenTogether`**，必须打到 `interface3.music.163.com`（**不用默认的 `cloudmusic` 业务名**）；NIM AppKey `3a6a3e48f6854dfa4e4464f3bdaec3b4`；随包携带 `libnim.dylib` / `libnim_chatroom.dylib`（NIM 10.9.40）
- **反证（实测）**：心跳响应只有 `{"code":200,"data":{"result":true,"timeSpan":30}}`——**没有任何歌曲/进度**；状态响应只有 `inRoom`/`roomInfo`/`anotherDeviceInfo`/`status:"CONNECTED"`，**无 songId、无 progress**

**⇒ 纯 HTTP 调用者的处境（实测）**：`tingxue-mcp` 发 `play/command/report` 得到 `{code:200,data:{result:true}}`，但**「对方客户端纹丝不动」**——因为真正的下发走 NIM，而纯 HTTP 调用者不是活跃房间成员。
`VPS-HTTP.md` §5 同结论：「**该方案仅支持作为被邀请方**」。

**⇒ 所以网易云后端的形态是：**

| 能做 | 不能做 |
|---|---|
| **作为被邀请方**加入官方房间 | **可靠地建房**（见下「矛盾」） |
| 用 `sync/playlist/get` **轮询快照** | 收到实时推送 |
| **本地锚定时间自行外推**（MeloX 的做法） | 驱动对端官方客户端（**实测纹丝不动**） |

**「矛盾」：HTTP 能否建房？**
- `VPS-HTTP.md`（实地踩坑）：「纯 API 建房和发送邀请虽然可能返回 `200`，但目前**无法维持可正常加入的有效房间**」
- `kui-2026/netease-together-mcp` 自述用小号建房 + 维持心跳——**但它同时声明是「代码与模拟测试版…不能承诺长期稳定」**
- **⇒ 倾向前者，但这是矛盾不是定论。落地前必须实测。**

> **⚠️ 还有一条会静默失效的现实障碍**：`ncm-mcp-server` 记录公开的 `NeteaseCloudMusicApi` 容器的 **eapi 加密参数已过期**，导致一起听与私信全部返回 400，它不得不自行重新实现 eapi/weapi。
> **这意味着「现成的第三方服务」不可依赖，eapi 得我们自己维护。** 这与 v1 设计文档 §13.1「上游是唯一不受我们控制、无版本号的东西」是同一条风险。

### 4.3 P2P 后端 —— 我们自己说了算

复用网格的栈（`iroh` 打洞 + 中继兜底、`spake2` 配对、`serde`+`postcard` 线格式）：

| 优势 | 说明 |
|---|---|
| **真推送** | 不需要轮询快照，同步精度是协议级的 |
| **持久容器** | 房间可以不随会话消失——这是网易云后端**做不到**的（官方没有群组接口，房间靠心跳续命） |
| **人数由我们定** | 不受服务端策略摆布 |
| **不碰账号边界** | 不操作对方的网易云账号 |
| **可用本地音乐** | 两端都持有同一文件时可直接对齐，不必都在线 |

**代价**：对方也得装 dslsmusic。

## 5. 同步：必须自建时钟（两个后端都是）

**核心事实**：`sync/playlist/get` 返回的 `playCommand` 是**最后一次被上报的命令的快照，不是时钟**。

所以正确做法是**本地锚定 + 外推**。MeloX 的实测参数可以直接借鉴：

```
以 playCommand 的 progress 为锚，用本地单调时钟外推当前应有位置
仅当 |本地外推 − 目标| > 0.35s 且（首次 || 命令已变）时才 seek
```

> **0.35s 这个阈值来自 MeloX 的实现，不是官方规范。** 我们应当把它做成可配参数并在实测中调，
> 而不是当成事实。**（v1 设计文档 §6.2 的 DSP 参数不该拍脑袋——同一条纪律适用于这里。）**

**何时对齐、多久对齐一次，两个后端不同：**

| | 网易云后端 | P2P 后端 |
|---|---|---|
| 触发 | 轮询 `sync/playlist/get`（MeloX 用 1Hz） | 对端推送 |
| 精度 | 受轮询周期与快照延迟限制 | 协议级 |
| 掉线恢复 | 重新拉快照 + 重新外推 | 重连后对表 |

## 6. 能力模型：降级，不拒绝运行

这是本项目**第四次**用同一条原则（前三次：`RenderTier`、音源的 `CapabilitySet`、音质档位）。

**一起听后端声明能力，UI 据此降级并如实告知用户。**

| 能力 | 网易云后端 | P2P 后端 |
|---|---|---|
| 发起会话 | **❓ 待实测**（HTTP 建房可能不可靠） | ✅ |
| 加入会话 | ✅（作为被邀请方） | ✅ |
| 实时推送 | ❌（只能轮询快照） | ✅ |
| 持久容器 | ❌（房间靠心跳续命） | ✅ |
| 与官方 App 用户互通 | ✅ | ❌ |
| 不碰对方账号 | ❌ | ✅ |
| 成员数 | 服务端策略，**不承诺** | 我们定 |
| 共享队列 | ✅ | ✅ |
| 音频 | 两端各自取流 | 两端各自取流 |

> **UI 必须在会话建立时就说清用的是哪个后端**，以及它的限制。
> 用户不该在「为什么对方不动」发生后才知道我用的是降级模式。

## 7. 网易云后端：接口与工程陷阱

### 7.1 全部 9 个接口（api-enhanced 440 模块全量核对，`ncm-api-rs` 的 `src/` 与之逐字对应）

| # | 方法名 | 线上路径 | 加密 | 方向 |
|---|---|---|---|---|
| 1 | `listentogether_room_create` | `/api/listen/together/room/create` | eapi | 写 |
| 2 | `listentogether_room_check` | `/api/listen/together/room/check` | eapi | 读（**仅房间存活**） |
| 3 | `listentogether_accept` | `/api/listen/together/play/invitation/accept` | eapi | 写 |
| 4 | `listentogether_status` | `/api/listen/together/status/get` | **weapi** | 读（**仅成员信息**） |
| 5 | `listentogether_heatbeat` | `/api/listen/together/heartbeat` | eapi | 写 |
| 6 | `listentogether_play_command` | `/api/listen/together/play/command/report` | eapi | **仅上报** |
| 7 | `listentogether_sync_list_command` | `/api/listen/together/sync/list/command/report` | eapi | **仅上报** |
| 8 | `listentogether_sync_playlist_get` | `/api/listen/together/sync/playlist/get` | eapi | **读 —— 唯一的状态读** |
| 9 | `listentogether_end` | `/api/listen/together/end/v2` | eapi | 写 |

**两个命名陷阱**：模块名是 `heatbeat`（**拼错**），线上路径是 `heartbeat`（拼对）；`end` 实际是 `/end/v2`。

### 7.2 工程陷阱（每一条都会导致功能坏掉）

1. **`commandInfo` / `playlistParam` 必须是序列化后的嵌套 JSON 字符串。** 把 `commandType` 等平铺到表单外层**通常返回 HTTP 400**。
2. **`version` 必须递增发送方自己的版本号，不能复用服务器返回值。** 原话：「复用未递增的 `version` 是两端列表不同步的最常见原因」。
3. **加歌要先 `ADD` 并等另一端同步，再发 `GOTO`。**
4. **⚠️ 不要照抄 `ncm-api-rs` 的 `sync_list_command`**：它把 `anchorSongId` 写死 `""`、`anchorPosition` 写死 `-1`（`src/api/listentogether_sync_list_command.rs:22-23`），而可用实现传的是**真实 anchor 值**（`anchorSongId: former`、`anchorPosition: current_index`）。**照抄很可能导致列表不同步。**
5. **`status/get` 的字段名上游拼错了**：是 `anotherDeviceInfo.antherUserId`（**`anther` 不是 `another`**）。
6. **没有「发送邀请」接口。** 只有 `play/invitation/**accept**`。客户端只能**手工拼链接**：
   ```
   https://st.music.163.com/listen-together/share/?songId=<ID>&roomId=<房间ID>&inviterId=<创建者ID>
   ```
   （官方会生成短网址以防滥用——**我们不复制那个短网址服务**。）

**「矛盾」`sync/playlist/get` 要不要带 `playlistParam`？**
- api-enhanced / `ncm-api-rs`：**只发 `roomId`**
- TinyCloudMusic 文档：**必须附带** `playMode`/`anchorSongId`/`anchorPosition`/`randomList`/`displayList`
- ⇒ 可能是「最小可接受」与「正确做法」之差。**倾向后者，但未实测。**

### 7.3 播放状态载荷

`commandInfo` = `{commandType, progress, playStatus, formerSongId, targetSongId, clientSeq}`

```
playStatus  ∈ { PLAY, PAUSE }
commandType ∈ { GOTO, ADD, REPLACE, PLAYMODE_CHANGE }
playMode    ∈ { ORDER_LOOP, RANDOM, SINGLE_LOOP }
```

## 8. 风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| **非会员方听不到 VIP 歌** | **官方行为是「跳过」**——无试听、无购买引导。且 fixtures 的 `roomVipAbGroup`（`huiyuan_ListenTogether_TSpop` 等）显示**网易自己还在 A/B 调这件事** | 无法缓解。**UI 必须提前说明**，不能让用户以为是 bug |
| **eapi 加密参数会过期** | 已实测：公开容器因参数过期导致一起听全部 400 | eapi 得我们自己维护；这是 v1 §13.1 同一条风险的又一次现身 |
| **一起听可被风控单独剥夺** | 有黑猫投诉实例。**但找不到任何「一起听导致封号」的报告**（明确标注 [未找到]） | 用户可见的降级提示；不自动重试到被封 |
| **对方账号** | 网易云后端**要操作对方的账号关系**（邀请/接受是账号级行为） | **会话建立前明确告知**；不自动加入任何房间 |
| **NIM 是私有通道** | 想复现真实下行要带 `libnim`。**我们不做**——那等于重实现一个 IM 客户端 | 网易云后端定位为**轮询快照的降级模式** |
| **人数上限不可知** | 服务端策略，不在协议里 | UI 不承诺 |
| **同步阈值无依据** | 0.35s 来自单一实现（MeloX），不是规范 | 做成可配参数，实测调 |

## 9. 未定项

| # | 未定项 | 为什么重要 |
|---|---|---|
| 1 | **网易云后端能否可靠建房** | 决定它是否只能「被邀请」。两个来源矛盾，**必须实测** |
| 2 | **`sync/playlist/get` 要不要带 `playlistParam`** | 两个来源矛盾，**必须实测** |
| 3 | **控制权模型** | 双人 vs 多人是否不同？专利提到「共识切歌」（CN114979083A）、`commandType` 里有 `REPLACE`/`PLAYMODE_CHANGE`——**但控制权归谁、能否夺权，未核实** |
| 4 | **队列里遇到「对方取不到的歌」怎么办** | 官方行为是「跳过」。我们要不要提示、要不要提前过滤？ |
| 5 | **P2P 后端的房间模型** | 持久容器？成员管理？复用网格的配对还是独立一套？ |
| 6 | **聊天** | 官方有文本/表情/语音，且**解锁制**（`unlockChatNeededMs`）。v1 做不做？P2P 后端要不要自己做？ |
| 7 | **时钟同步的具体协议**（P2P 后端） | 需要选一个：粗略的 NTP 式对表，还是更简单的「锚点 + 单调钟外推」 |
| 8 | **本地音乐** | P2P 后端能用本地文件，但「对方没有这个文件」时的降级路径未定 |
| 9 | 与 v1 音质档位的关系 | 一起听时用哪一档？跟随谁的设置？（设计文档 §4.5 的两根轴在这里第一次交叉） |

## 10. 落地顺序（建议）

**不排里程碑**——本设计的未定项太多，先收敛再排。

一个初步直觉：

```
1. 实测未定项 1、2（网易云建房可靠性 / playlistParam）—— 成本低，决定整个后端形态
2. P2P 后端的时钟同步原型（与网格的 M2-M4 可并行）
3. 网易云后端（被邀请方 + 轮询快照）
4. UI：能力声明驱动降级
```
