# dslsmusic 一起听 设计文档

- 日期：2026-09-26
- 状态：草案，未定项见 §9
- 关系：独立于 v1 设计文档与网格文档。它复用网格的 P2P 栈，但**不是**网格的一部分——网格是「你自己的设备之间」，一起听是「不同的人之间」。

---

## 1. 这是什么 / 为什么单独立一份

用户要一起听，且**两种后端都要**：走网易云官方的，和走我们自己 P2P 的。

一开始我把它当成「网格的同步播放」——但那是错的，有两条硬区别：

| | 网格 | 一起听 |
|---|---|---|
| 参与者 | **你自己的**多台设备 | **不同的人** |
| 出声 | 同一时刻只有一台 | **两端同时出声** |

而且调研推翻了网格文档里一条论断（见 §2）。

---

## 2. ⚠️ 先更正一处既有错误

网格文档 §3.3 写着：

> 「若将来要做同步播放（两端都出声），音频就必须传——那是另一个量级的工程（时钟同步、抖动缓冲）」

**这句话是错的**，至少对一起听是错的。

**已核实**：每一条会出声的实现都是**自己拉自己的流**——
`s12mmm3/QListenTogether`（`Main.qml:214` 调 `song_url_v1`）、`youshen2/MeloX`（`PlayerStore.swift:432` 打 `/api/song/enhance/player/url/v1`）。
`NeteaseListenTogetherAPI.swift` **全文没有任何房间音频/中继端点**。

**所以音频不必传——要同步的是时间线。** 那一整句「另一个量级的工程」的推理起点就是假的。
（它只在「一端持有本地文件、另一端没有」时成立。）

> **但这不代表它便宜。** 取代「音频传输」的是一个同等分量的东西：
> **两端各自取流 ⇒ 队列里只能放两端都能取到的歌**，且**时钟必须我们自己造**（见 §5）。

## 3. 双人版与多人版：**是两套设计，不是一套加参数**

> **⚠️ 本节修正一处我自己的错判。** 我起初根据官方那句「由双人一起听**升级**到
> 多人一起听」，把它建模成「一个功能 + 一个成员数」。**那是错的**——
> 「升级」指的是双人房可以**转换为**多人房，而不是版本号递增。

**产品名层面是三个，实现层面是两个** —— 这组数字要分清楚：

| 产品名 | 时间 | 实现层面 |
|---|---|---|
| **一起听** | 2020-07-10 | 一条分支 |
| **多人一起听** | 2023-10 | 另一条分支 |
| **车载一起听** | **2026-09-21** | **多人分支的车机形态**（官方原话：「在保留**多人**听歌核心玩法的基础上，将一起听**场景拓展至车内场景**」） |

另有**一个模式名**「和陌生人一起听」（2021-02，官方称「操作步骤和『一起听』一致」）。

**三条独立证据链都说实现层面只有两条分支**（全部自验）：
1. **官方 PC 客户端全量扫描**（213 chunk / 17.85 MB / 解码后 1.72 亿字符）：
   deep-link action 共 23 个，与一起听相关的**只有 2 个**；端点**恰好 17 个**
   `/api/listen/together/*`，**无 `multi/*` 子树**
2. **官方 AndroidManifest**（`com.netease.cloudmusic`）：
   `ListenTogetherInviteActivity` **与** `ListenTogetherMultiInviteActivity` ——
   **两个独立邀请 Activity**
3. **第二份独立 Manifest**：逐字相同

**⚠️ 两个容易搞错的名字：**
- **「跟听」不是网易的，是酷狗的。** 酷狗 2021-01 上线「跟听」，网易 2021-02-02
  公开发文指控其「像素级」模仿「一起听」。两份 Manifest 里 `followlisten` 均为 **0**。
- **不要为了凑三个把「云村自习室」算进来。** 官方把它定位为「音乐+社交」**独立产品**，
  其文案全文**没有「一起听」**（全量扫描里 `自习室`=0、`云圈`=0）。

#### 端点层：**两套路径**（已查清）

来源：`MiaoSIKI/YesPlayMusic-listen-together-support` 的 `src/utils/listenTogether.js`（1287 行）
—— **一个同时实现了双人与多人的真实代码**。真实性佐证：它**独立使用了
`code === 488 → 房间失效`**，而 488 只在我们从**官方 PC bundle** 挖出的代码里出现过；
换一个未公开错误码，编造的实现不会恰好命中。

**多人族端点（`multi/match/*`）**：
`ack`（加入）/ `status/get` / `heartbeat` / `exit`（`exitType=NORMAL_END`）/
`song/operate`（`operate:1` = SONG_ADD）

**与那 9 个的重合只有 `play/command/report` 一个。** 其余 8 个要么双人独有
（`room/create`、`room/check`），要么多人换名另起（加入/退出/状态/心跳/列表变更）。

> **⚠️ 多人没有建房接口 —— 靠接受邀请进入。**
> 这对模式 2 是个**产品级限制**（见 §4.2）。

| | 双人 | 多人 |
|---|---|---|
| `roomId` 形状 | 普通串 | **`32位hex_13位时间戳`** |
| 成员字段 | `roomUsers[]` | `multiLtRoomUserAgg.onlineUserInfos[]` |
| 响应外层 | — | 多包一层 `multiLtRoomSnapshot{...}` |
| 邀请参数名 | `inviterId` | **`inviterUid`** |
| 分享链接 | `/share/` | `/multishare/index.html` |
| `chatRoomId` | ✅ | ✅（**NIM 是共用基础设施**） |

**⭐ 最关键的差异：心跳语义相反。**

| | 双人 | 多人 |
|---|---|---|
| `heartbeat` 载荷 | `{roomId, songId, playStatus, progress}` | `{roomId}` |
| 语义 | **上报**（响应不带状态） | **拉取**（房间当前歌曲来自响应 `roomPlaySongInfo`） |
| 间隔 | 20s | 8s |

代码注释原文：「多人群房的权威队列来自 heartbeat 的 `roomSongInfo`，
**不再轮询 legacy `sync/playlist`**」—— **这就是为什么 `sync/playlist/get` 对多人直接跳过。**

**⇒ 实现层结论：端点层两套，代码层一套。** 该实现是一个 service class +
一个 `_multi` 布尔标志，约 **10 处 `if (this._multi)`** 分叉到平行端点集。
**是「同一份骨架、两条端点路径」，不是「一套接口加个参数」。**

> **⚠️ 依据强度（照录调研判断）**：`multi/match/*` 是**双源第三方一致**
> （该实现 + WaveForge），官方 bundle **间接支持**（`/api/listen/together/` 前缀、
> `music_listenTogether_multi_invite` 业务名），但**没有官方来源直接展示过这 5 条路径**；
> 官方 PC 端因不支持多人而查不到（`multi/*` 命中 0，**这不算反证**）。
> **⇒ 视为「双源第三方证实、官方未直接确认」。**
> **建议落地前先做一次实机抓包**（小号建多人房，抓 `multi/match/ack` 真实流量）。

**「一起听」与「多人一起听」是两个不同的东西：**

- **[自验] 两个不同的 deep-link action**，在官方 PC 客户端的 **3 个独立 chunk
  （35/37/65）**各自验证到：`multilistentogether`→`multiListenTogether` 与
  `listentogether`→`listenTogether`
- **两棵接口子树**：多人有自己的一整套 `multi/*`
- **分享链接形态不同**：多人是 `inviterUid` + `roomId_<timestamp>`
- **控制模型不同**（见下）

**⇒ 不能用一个成员数参数糊过去。**

**⚠️ 控制模型：未知。**（本节结论已被**撤回**，见下）

流传的「多人房轮流控歌」**能确定的是它的来源**：在一份 `SoundFieldLab/WaveForge`
文档里，`轮流` 全文只出现一次、且在**表格右列**——那是**WaveForge 自家的 P2P 插件
设计**（「我推荐=按入房顺序轮流、每人 1–3 首」），**不是网易的行为**。
**「轮流是误传」这个判断成立。**

> **⚠️ 但本节早先据此写下的正向结论「多人 = 房主独控 + 可授权」已被撤回。**
>
> 调研代理自己回头核了那份来源：**该 org 创建于 2026-08-30、只有 2 个仓库、5 star**，
> 文档是**他们给自己插件写的功能提交**，`follow/listen/*` 在全 GitHub **仅此一处**。
> 用官方 bundle 交叉验证：它的**双人端点清单全部被证实**（`privilege/get`、
> `privilege/change/report`、`sync/notice`、`invite/message/send` 都在官方 PC 端里），
> **但 `multi/*` 无法验证**（PC 端不支持多人，查不到是必然）。
>
> **⇒ 「房主独控 + 可授权」是单源、低可信、且自述「未实测 UI」。降级为未证实。**
>
> ⚠️ 且**不能**用「PC 客户端里 `房主`/`轮流` 命中为 0」来反证——那是**没有证明力的
> 负结果**，因为 PC 端根本不支持多人（见下）。
>
> **⇒ 多人的控制模型，目前是空的。落地前必须实测。**
>
> **⚠️ 而且现在有了反向证据**：上面那个**真做了双人+多人**的实现里，
> **接口里根本没有 `isOwner` 字段** —— 服务端只给 `creatorId`，客户端自己算一个
> `togetherOwner` **纯用于展示**。该实现**没有任何 owner 拦截**，双人和多人
> **都是任何成员可加歌/置顶**。
>
> **[推断] 真正的权限判定只可能在服务端** —— 佐证是多人 `song/operate` 会返回
> `{result:false, failedMsg}`，说明服务端**有能力拒绝**。
>
> **⇒ 所以「房主独控」不仅未证实，而且有证据表明它至少不是客户端强制的。**
> **按「任何成员都可操作、服务端可能拒绝」来设计**，比按「房主独控」安全：
> 前者遇到服务端拒绝时还有退路，后者会让 UI 假装有权限、然后被服务端打回。

> **方法论注记**：曾有子代理用「官方 PC 客户端里 `房主` 命中 0」来反证轮流说。
> 复现确认了 0 命中，**但这个负结果没有证明力**——因为 **PC 端根本不支持多人**（见下）。
> 在适用范围内确认的是：`房主/轮流/控歌/轮麦/排麦/管理员/房间号/邀请码/群聊/匹配`
> 在 PC 端全部为 0。

**⚠️ PC 端显式拒绝多人，这直接限制我们的价值主张：**

```
case "multiListenTogether": c.L.error("暂不支持多人一起听，敬请期待！")
```
macOS 端**连双人都不支持**（「3.0版本暂不支持」）。

**⇒ 「与官方 App 用户互通」只在移动端成立。** 我们做多人一起听，
**用官方 PC 客户端的用户进不来**。这一条必须在 UI 上说清，否则会变成「为什么他加不进来」。

**人数上限：无定论，本设计不承诺。** 官方说「突破人数限制」但**没给数字**；
`5` 与 `6` 两个数字**都只来自 AI 内容农场**，一手来源里都没有。云信 B2B 文档说 2 人，
**但那是 B2B 不是消费端**。专利实施例 10 人。
⚠️ 且 9 个 HTTP 接口里**没有任何一个带人数参数**——人数是服务端策略，不在客户端协议里。
**⇒ 不要把人数当协议常量；UI 上不做承诺。**

**陌生人匹配：存在，且是服务端的，第三方做不了。** 专利 CN114979083A 权利要求 1
即服务端匹配，`roomInfo` 里还带 `matchedReason`/`alg` 字段（服务器告知「为何匹配」）。
**[推断] 它需要匹配服务 + NIM 聊天室 + Agora 三重依赖，不是我们能复刻的。**

**两处专利与上线行为不符**（记录在案，不要拿专利当行为依据）：
2020 年 CN111797271A 描述 N 人**对称**控制，与已上线的**房主独控**冲突；
2022 年专利的「共识切歌」在任何接口或字符串里都不存在，[推断] 仅停留在专利。

## 4. 三种一起听

> **框架修正**（用户 2026-09-26 指出）。本文档早先把形态写成「**两个后端**
> （网易云 / 我们自己 P2P）」。**那个框架是错的** —— 它把「双人一起听」与
> 「多人一起听」算成了同一套，而 §3 已经证明**它俩是两套设计**
> （两个不同的 deep-link action、多人有自己一整套 `multi/*` 接口子树、
> 分享链接形态不同、控制模型不同）。
>
> **正确的分层是三种模式**：

| # | 模式 | 房间归谁 | 与官方 App 用户互通 | 持久 | 真推送 |
|---|---|---|---|---|---|
| 1 | **双人一起听** | 网易 | ✅（**仅移动端**，PC 端连双人都禁） | ❌ | ❌ |
| 2 | **多人一起听** | 网易 | ✅（**仅移动端**，PC 端显式拒绝） | ❌ | ❌ |
| 3 | **dslsmusic 专属一起听** | **我们** | ❌ | ✅ | ✅ |

**模式 1 与 2 共享的是「账号边界」这个性质**（都操作对方的网易云账号、
都受风控约束、都拿不到实时下行），**不共享实现**。

> ⚠️ **一处未核实**：模式 1 与 2 在**接口层的重叠度**我们没查
> （那 9 个 `listentogether_*` 端点是两者共用、还是多人另有 `multi/*` 一族）。
> 在查清之前，**不要在代码里把「人数」做成一个参数** —— 那正是本文档早先
> 犯过的错（§3）。**这是落地前必须补的一项。**

### 4.1 三种模式共同的部分（**都要自己实现**）

**这是本设计最重要的一条结论：即使是网易云后端，同步层也得我们自己写。**

```
共享队列 + 时间线（歌曲、起始位置、起始时刻）+ 控制权
                    ↓
        两端**各自**从音源取流 → 各自出声
```

**不传音频、不传音源凭证。** 每一端用自己的账号、按自己的音质设置取流。

### 4.2 模式 1 / 2：网易云后端 —— 比预想的弱得多

**它拿不到实时下行。** 真实下行是**私有的 NIM（网易云信 IM）通道**，不是 HTTP：

- `TinyCloudMusic`（唯一复现真实通道的实现）：`/api/middle/im/token/get`，**`bizName=music_listenTogether`**，必须打到 `interface3.music.163.com`（**不用默认的 `cloudmusic` 业务名**）；NIM AppKey `3a6a3e48f6854dfa4e4464f3bdaec3b4`；随包携带 `libnim.dylib` / `libnim_chatroom.dylib`（NIM 10.9.40）
- **反证（实测）**：心跳响应只有 `{"code":200,"data":{"result":true,"timeSpan":30}}`——**没有任何歌曲/进度**；状态响应只有 `inRoom`/`roomInfo`/`anotherDeviceInfo`/`status:"CONNECTED"`，**无 songId、无 progress**

**⇒ 纯 HTTP 调用者的处境（实测）**：`tingxue-mcp` 发 `play/command/report` 得到 `{code:200,data:{result:true}}`，但**「对方客户端纹丝不动」**——因为真正的下发走 NIM，而纯 HTTP 调用者不是活跃房间成员。
`VPS-HTTP.md` §5 同结论：「**该方案仅支持作为被邀请方**」。

**⇒ 所以模式 1 / 2 的形态是：**

| 能做 | 不能做 |
|---|---|
| **作为被邀请方**加入官方房间 | **可靠地建房**（见下「矛盾」） |
| 用 `sync/playlist/get` **轮询快照** | 收到实时推送 |
| **本地锚定时间自行外推**（MeloX 的做法） | 驱动对端官方客户端（**实测纹丝不动**） |

**「矛盾」：HTTP 能否建房？**
- `VPS-HTTP.md`（实地踩坑）：「纯 API 建房和发送邀请虽然可能返回 `200`，但目前**无法维持可正常加入的有效房间**」
- `kui-2026/netease-together-mcp` 自述用小号建房 + 维持心跳——**但它同时声明是「代码与模拟测试版…不能承诺长期稳定」**
- **⇒ 倾向前者，但这是矛盾不是定论。落地前必须实测。**

> **⚠️ 还有一条会静默失效的现实障碍**：`ncm-mcp-server` 记录公开的 `NeteaseCloudMusicApi` 容器的 **eapi 加密参数已过期**，导致一起听与私信全部返回 400，它不得不自行重新实现 eapi/weapi。
> **这意味着「现成的第三方服务」不可依赖，eapi 得我们自己维护。** 这与 v1 设计文档 §13.1「上游是唯一不受我们控制、无版本号的东西」是同一条风险。

### 4.3 模式 3：dslsmusic 专属一起听（**房间与同步**是我们自己的）

> **⚠️ 一处更正**（用户 2026-09-26 指出）。本节早先把「可用本地音乐」列成本模式的
> **优势**，那读起来像是它的音频走本地文件。**不对**：
>
> **模式 3 的音频同样从网易云下载。**
> **「独立」指的是房间与同步层，不是音频来源。**

**这个区别很重要**，因为它说明：**三种模式在音频那一层是同一件事**，
差别只在房间归谁、同步谁做。

```
音频（三种模式完全一样）
  各端各自从网易云取流 —— 不传音频、不分享凭证
  ⇒ 队列里只能放两端都能取到的歌

房间 + 同步（← 只有这一层是三种模式的区别）
```

| | 模式 1 | 模式 2 | **模式 3** |
|---|---|---|---|
| 房间归谁 | 网易 | 网易 | **我们** |
| 同步谁做 | 网易（但只给快照） | 网易（但只给快照） | **我们（真推送）** |
| 音频从哪来 | 网易云，各自取流 | 网易云，各自取流 | 网易云各自取流；**本地文件走推送** |
| **支持本地音乐** | ❌ | ❌ | ✅ **独有** |

> **⇒ Task 7 做的 `stream_url` 那条路，三种模式共用。** 这是好事——它已经落地了。

**模式 3 的独立之处**（用我们自己的房间与同步层，复用网格的栈：
`iroh` 打洞 + 中继兜底、`spake2` 配对、`serde`+`postcard` 线格式）：

| 优势 | 说明 |
|---|---|
| **真推送** | 不需要轮询快照，同步精度是协议级的 |
| **持久容器** | 房间可以不随会话消失——这是模式 1/2 **做不到**的（官方没有群组接口，房间靠心跳续命，失效只能开新房） |
| **人数由我们定** | 不受服务端策略摆布 |
| **不碰账号边界** | 不操作对方的网易云账号 |

#### 模式 3 **独有**的能力：本地音乐也能一起听（靠推送）

**这是模式 1 / 2 做不到的。** 网易的房间没有传递音频的手段，所以
「网上根本没有的歌」（你自己的录音、下架的歌、私有文件）在官方一起听里
**放不进队列**；而模式 3 可以——**因为房间是我们的，我们能把字节送过去。**

```
音频层的完整规则（与网格文档 §3.5 同一条原则）
  ├─ 音源取得到（网易云有）→ 各端**各自取流**，不传音频
  └─ **确认**是真正本地的（网上根本没有）→ **才推送**
```

> **⚠️ 「先自己取、取不到才传」不只是省带宽 —— 它是营收判据的一部分。**
>
> | 情况 | 若各端自取 | 若我们对端推送 |
> |---|---|---|
> | 歌在网易云（含 VIP） | 对方按**他自己的**会员等级取 → 非会员取不到 → **没绕过付费** ✅ | **绕过付费** ❌ |
> | 歌根本不在网易云（本地文件） | 取不到 | 只能推 → **没有可绕的东西** ✅ |
>
> **⇒ 「确认是真正本地的」这个前提不是谨慎，是那条线的位置本身。**
> 只要歌在网易云，就必须让对端自己去取——**哪怕我们能把文件传过去更快**。
> 推过去就变成了「用 A 的会员给 B 听」。

**代价**：对方也得装 dslsmusic；
且**对「网易云有的歌」，队列限制与模式 1/2 完全相同**（两端都得能取到）。
**模式 3 多出来的只是「网易云没有的东西」那一类。**

### 4.4 为什么「持久容器」只能自建 —— 网易的两个对象是**不连通的**

用户问过网易有没有**群组**（直觉是：拿群组当共享队列的容器）。核实结论是**没有**，
而且原因比「没做」更根本。

**① 没有「群组」这个接口。** [自验] api-enhanced **440 个 module** 里：
- `group` 只命中 `video_group` / `video_group_list` —— 读了源码，那是**视频分类**
  （`/api/videotimeline/videogroup/otherclient/get`）
- `circle` 命中 **0**

另有 3 个主流 fork（`NeteaseCloudMusicApi_V8`、`hudawei996`、`react-music`）与
`ncm-api-rs` **完全一样**。

**② 存在的是「云圈」——但它是内容社区，不是容器。** 官方页确实有云圈（成员关系 + 群聊），
而后端类型定义（`XiaoMengXinX/Music163Api-Go` 的 `types/circleGet.go`）[自验] **只有
`count{post, read, member, online}` 四个计数器，没有任何队列/歌单/播放态字段**，
其自述就是「获取云圈**动态**API」。
（旁证：官方 PC 客户端最大的 22 个 chunk 里，`云圈`/`群聊`/`圈子` 命中 **0**。
范围声明：22/205 chunk。）

**③ 共享歌单存在——但它是歌单，不是队列。** 官方名就叫「共享歌单」（v8.2.55 起，
服务端有 `sharedUsers` 字段）。**但没有 progress、没有 playStatus、没有心跳。**
这是网易**最接近共享队列**的东西，而它**不同步播放**。

**④ ⭐ 房间不能持久化（最硬的一条）。** [自验] 官方 PC 客户端原文：

```
错误码 488 → ROOM_LOSS → 「一起听已失效，可邀请好友进入新的一起听」
```

**失效后只能开**新的**房间，不能回原房。** 佐证：状态枚举
`alone/timeout/together/waiting`、`renew_invite`、离开原因 `TIMEOUT_LEAVE_CHECK`，
以及 UI 里「上次一起听」那个按钮写的是**「邀请」而不是「重进」**；
心跳一停就掉房。

**⇒ 结论：网易的「有播放态的」和「能持久的」是两棵不相交的树。**

| | 有播放态 | 能持久 |
|---|---|---|
| 一起听房间 | ✅ | ❌（488/ROOM_LOSS） |
| 云圈 / 共享歌单 | ❌ | ✅ |

> **⚠️ 本节结论在 §4.6 被部分修正**（用户 2026-09-26 提出「协作歌单」后重新评估）。
> 「有播放态的」和「能持久的」确实是两棵树 —— 但**共享歌单那棵树是可以借用的**：
> 我们不必自建容器，可以**借网易的共享歌单当持久层，自己只补播放态**。
> 见 §4.6。

**所以「我们这群人的长期共享队列」在网易那边没有现成对应物。**
本节原写的「只能自建」在 §4.6 被修正为「**可以借用共享歌单**」——
这正是 §4.3 模式 3 **不可替代**的价值所在（不是「另一个选项」）。

> **⚠️ 一处更正**：本项目早先（基于纯搜索）说过「群组模式一起听最多 5 人、轮流控歌、
> 歌单由所有人共同维护」。**这三条都不可靠**——人数来源是 AI 内容农场（见附录），
> 轮流控歌是误传（见 §3），而「歌单共同维护」混淆了共享歌单与一起听队列。

### 4.5 模式 3 的功能空间：**官方做不到的，才是我们的**

用户 2026-09-26 定调：「**主要是可以做很多官方不支持的功能。**」

**但「官方不支持」有两种，得分开看** —— 这决定先做哪个：

| 类型 | 例子 | 优势能维持多久 |
|---|---|---|
| **技术上做不到** | 第三方拿不到实时下行（私有 NIM 通道）、房间易失 | **持久** —— 除非网易重做架构 |
| **产品上不做** | PC 端拒绝多人、非会员直接「跳过」、聊天解锁制 | **可能被一次更新关掉** |

**⇒ 力气应该先花在「技术上做不到」的那些上。**

#### A. 护城河（技术性不可能，别人抄不走）

**① 持久容器** —— 最大的一条。

官方房间靠心跳续命、**失效只能开新房**（错误码 `488` → `ROOM_LOSS` →
「一起听已失效，可邀请好友进入新的一起听」），而且它**没有群组可以当容器**：
440 个接口模块里 `group` 只命中 `video_group`（**视频分类**），`circle` 命中 **0**。

| 功能 | 说明 |
|---|---|
| **长期共享队列** | 「我们这几个人的歌单」，随时进去接着听 —— 房间不再是一次性的 |
| **异步一起听** | 不用同时在线：你加歌、我回头听。**官方的定义就是「同时」，我们不必** |
| **房间历史** | 上次听到哪、谁加了什么、什么时候 |

> **「异步」这条值得单独说**：它不是「一起听」的变体，而是**它与共享歌单交汇处
> 的新东西** —— 官方那边「共享歌单」和「一起听队列」是**两个不连通的对象**
> （前者有持久没播放态，后者有播放态没持久，见 §4.4）。**我们能合成一个。**

**② 音频来源不受曲库限制**

| 功能 | 说明 |
|---|---|
| **本地文件一起听** | 网易房间传不了音频 ⇒「网上根本没有的歌」在那边**放不进队列** |
| **混合队列** | 曲库歌 + 你的录音 + 播客，同一个队列 |
| **跨音源** | 网易云 + 本地 + 未来其他音源，一个房间 |

**③ 同步质量** —— 官方第三方只能轮询快照、**拿不到时钟**（§4.2）。我们是真推送。

#### B. 可能被官方补上的（做了有价值，但**不是护城河**）

| 功能 | 官方为什么不做 |
|---|---|
| **人数不设限** | 服务端策略；那 9 个接口里**没有任何人数参数** |
| **PC 端进多人房** | 官方 PC 端**显式拒绝**（`"暂不支持多人一起听，敬请期待！"`）；macOS 连双人都不支持 |
| **控制模型可选** | 官方只有两种（双人双向 / 多人房主独控 + 可授权），我们可以给全：轮流、自由、按入房顺序… |
| **权限粒度** | 谁能加歌、谁能切歌 |

**⇒ 别把 B 类当护城河** —— 一次官方更新就能抹平。

#### C. 建议的优先顺序

1. **持久共享队列 + 异步一起听** —— 同时踩中两个官方做不到的事
   （房间易失 + 歌单与队列不连通），而且**不依赖实时性**，可以先做
2. **本地文件一起听** —— 让模式 3 有「官方给不了」的实质内容；
   那条营收边界我们已经验证过（§4.3：只在**确认真正本地**时才推送）
3. **控制模型可配** —— 成本极低（同步层本来就要自己写），但**感知最强的差异**

#### D. ⚠️ 一条**不该**做的（**理由已更正**）

**不要做「帮对方取到 VIP 歌」。** 那是拿你的会员给他听 —— **§4.3 那条线的另一侧。**

> **⚠️ 本节早先还写了第二条理由：「加购买引导 ⇒ 我们不是他的付费渠道，没有立场做」。
> 那条理由是错的，已删。**
>
> 复查发现：**官方非会员遇到 VIP 歌并非「无购买引导」——它有整套 VIP 转化流程**：
> 提示按 `me` / `opposite` / `both` **三分**（谁缺会员就提示谁）、弹收银台，
> 文案包括「开通黑胶VIP一起听」**和「送 TA 黑胶VIP 一起听」**，
> 并有 `vip/gift/report` 接口与 NIM 消息类型 `VIP_GIVE=20004` / `DIGITAL_GIVE=20005`。
>
> **⇒ 更正为：网易不共享权益，但主动促成购买与赠送。** 而且这是**营收正向**的行为
> ——「送 TA 黑胶VIP」是个相当聪明的设计：它把「对方听不了」这个摩擦
> **转化成了收入**。
>
> **那我们要不要也做购买引导？** 这是一个**新的、独立的决定**，
> 不该由我早先那条错理由顺手否掉。我的倾向是**不做**，但理由不同：
> **那意味着要驱动网易的收银台/支付流程**，而支付流程是第三方客户端
> 最不该碰的一类东西（金额、退款、法务都在那儿）。
> **这是「风险类别不同」，不是「没立场」。** 留给你定。

### 4.6 候选方案：**借网易的共享歌单当持久容器**（前提未核实）

用户 2026-09-26 提到「协作歌单」。核实后确认官方名是「**共享歌单**」，
而它恰好补上了 §4.4 缺的那一半。

**核实到的事实**（来源见 `.superpowers/sdd/research-together-report.md` §4）：

| 项 | 内容 |
|---|---|
| 官方文案 | v8.2.55（2021-07-14）「**「共享歌单」歌单可以多人协作啦**」；v8.5.30「来跟**一起听歌的好友**创建属于你们的共享歌单」 |

| 服务端字段 | `sharedUsers` / `historySharedUsers` / `shareCount` / `sharedPrivilege`；Kotlin 模型有 `shareStatus` |
| 会员门槛 | **非黑胶会员也有 30 天体验** |
| ⚠️ 关键限制 | **它是歌单，不是队列** —— 无 `progress`、无 `playStatus`、无心跳、无房间。**异步协同编辑。** |

#### 拼法

| 层 | 谁提供 |
|---|---|
| 持久 / 多人可编辑 / **官方 App 里看得见** | **网易的共享歌单** |
| 播放态（进到哪、在放什么、同步） | **我们** |

**这比从零自建容器好在三点：**

1. **对方能在官方 App 里直接加歌** —— **不需要装 dslsmusic 就能贡献内容**。
   这直接绕开了 §4.3 那条「模式 3 要求对方也装」的最大门槛。
2. **持久性不用我们保证** —— 存在网易那儿，我们崩了它还在。
3. **它天然是「异步一起听」的形状** —— 共享歌单本来就是异步协作编辑的，
   我们补上播放态，正好就是 §4.5 里那条「**把两个不连通的对象合成一个**」。

#### ⚠️ 一个未核实的前提，它可能让上面全部作废

调研明确记录：**[未找到] 任何邀请/接受接口** —— 邀请流程在 App 侧、未公开。

| 如果能从第三方创建/共享 | 如果不能 |
|---|---|
| 我们在客户端里直接建房建单，体验完整 | **用户在官方 App 里建好共享歌单，我们在客户端里读它 + 补播放态** —— 也能用，只是多一步手工 |

**第二种也能接受**（「你先在官方 App 里建个共享歌单、把歌加进去，然后在我们这儿选它开一起听」），
**但未核实**。已派代理去查「第三方能不能创建 / 开启共享 / 邀请协作者」，结论落回本节。

#### 待查清单

1. 第三方能否 **创建歌单**（这一条大概率可以，是标准接口）
2. 第三方能否 **开启「歌单共享」这个开关** —— 这是关键，决定上面走哪一列
3. 协作者的**邀请/接受**有没有接口（调研说没有；确认一遍）
4. 协作者**人数上限**（网传 4 人**只见于内容农场**，不作证据）

6. 共享歌单的**曲目是否可读**（`PlaylistDetailResp` 有 `sharedUsers`，但曲目列表接口是否对协作者开放）

> ⚠️ **一条边界**：无论走哪一列，**音频仍然各端自取**（§4.3）。
> 借用共享歌单借的是**容器**，不是音频 —— §4.3 那条营收线一点没动。

## 5. 同步：必须自建时钟（三种模式都要）

**核心事实**：`sync/playlist/get` 返回的 `playCommand` 是**最后一次被上报的命令的快照，不是时钟**。

所以正确做法是**本地锚定 + 外推**。MeloX 的实测参数可以直接借鉴：

```
以 playCommand 的 progress 为锚，用本地单调时钟外推当前应有位置
仅当 |本地外推 − 目标| > 0.35s 且（首次 || 命令已变）时才 seek
```

> **0.35s 这个阈值来自 MeloX 的实现，不是官方规范。** 我们应当把它做成可配参数并在实测中调，
> 而不是当成事实。**（v1 设计文档 §6.2 的 DSP 参数不该拍脑袋——同一条纪律适用于这里。）**

**何时对齐、多久对齐一次，两个后端不同：**

| | 网易云后端 | P2P 后端 |
|---|---|---|
| 触发 | 轮询 `sync/playlist/get`（MeloX 用 1Hz） | 对端推送 |
| 精度 | 受轮询周期与快照延迟限制 | 协议级 |
| 掉线恢复 | 重新拉快照 + 重新外推 | 重连后对表 |

这是本项目**第四次**用同一条原则（前三次：`RenderTier`、音源的 `CapabilitySet`、音质档位）。

## 7. 网易云后端：接口与工程陷阱

### 7.1 全部 9 个接口（api-enhanced 440 模块全量核对，`ncm-api-rs` 的 `src/` 与之逐字对应）

| # | 方法名 | 线上路径 | 加密 | 方向 |
|---|---|---|---|---|
| 1 | `listentogether_room_create` | `/api/listen/together/room/create` | eapi | 写 |
| 2 | `listentogether_room_check` | `/api/listen/together/room/check` | eapi | 读（**仅房间存活**） |
| 3 | `listentogether_accept` | `/api/listen/together/play/invitation/accept` | eapi | 写 |
| 4 | `listentogether_status` | `/api/listen/together/status/get` | **weapi** | 读（**仅成员信息**） |
| 5 | `listentogether_heatbeat` | `/api/listen/together/heartbeat` | eapi | 写 |
| 6 | `listentogether_play_command` | `/api/listen/together/play/command/report` | eapi | **仅上报** |
| 7 | `listentogether_sync_list_command` | `/api/listen/together/sync/list/command/report` | eapi | **仅上报** |
| 8 | `listentogether_sync_playlist_get` | `/api/listen/together/sync/playlist/get` | eapi | **读 —— ⚠️ 仅双人**（多人**不用它**，多人的状态来自 `multi/match/heartbeat` 的响应，见 §3） |

### 7.2 工程陷阱（每一条都会导致功能坏掉）

1. **`commandInfo` / `playlistParam` 必须是序列化后的嵌套 JSON 字符串。** 把 `commandType` 等平铺到表单外层**通常返回 HTTP 400**。
2. **`version` 必须递增发送方自己的版本号，不能复用服务器返回值。** 原话：「复用未递增的 `version` 是两端列表不同步的最常见原因」。
3. **加歌要先 `ADD` 并等另一端同步，再发 `GOTO`。**
4. **⚠️ 不要照抄 `ncm-api-rs` 的 `sync_list_command`**：它把 `anchorSongId` 写死 `""`、`anchorPosition` 写死 `-1`（`src/api/listentogether_sync_list_command.rs:22-23`），而可用实现传的是**真实 anchor 值**（`anchorSongId: former`、`anchorPosition: current_index`）。**照抄很可能导致列表不同步。**
5. **`status/get` 的字段名上游拼错了**：是 `anotherDeviceInfo.antherUserId`（**`anther` 不是 `another`**）。
6. **⚠️ 更正**：官方客户端**有**邀请接口 —— `apiListenTogetherInviteMessageSend({roomId, acceptorId})`。
   但**全 440 个 module 里 `invite` 命中 0**——**该接口未被任何 API 包装收录**，
   真实 URL 未知（不声称知道）。
   **⇒ 对我们的实际影响不变**（用不了就是没有），但原因要记对：
   **不是网易没做，是包装没跟上。**
   当前 9 个接口里只有 `play/invitation/**accept**`（且带 `refer:"inbox_invite"`，
   暗示邀请原本走私信）。所以只能**手工拼链接**：
   ```
   https://st.music.163.com/listen-together/share/?songId=<ID>&roomId=<房间ID>&inviterId=<创建者ID>
   ```
   （官方会生成短网址以防滥用——**我们不复制那个短网址服务**。）

**「矛盾」`sync/playlist/get` 要不要带 `playlistParam`？**
- api-enhanced / `ncm-api-rs`：**只发 `roomId`**
- TinyCloudMusic 文档：**必须附带** `playMode`/`anchorSongId`/`anchorPosition`/`randomList`/`displayList`
- ⇒ 可能是「最小可接受」与「正确做法」之差。**倾向后者，但未实测。**

### 7.3 播放状态载荷

`commandInfo` = `{commandType, progress, playStatus, formerSongId, targetSongId, clientSeq}`

```
playStatus  ∈ { PLAY, PAUSE }
commandType ∈ { GOTO, ADD, REPLACE, PLAYMODE_CHANGE }
playMode    ∈ { ORDER_LOOP, RANDOM, SINGLE_LOOP }
```

## 8. 风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| **非会员方听不到 VIP 歌** | **官方行为是「跳过」** —— **⚠️ 但「无购买引导」是我早先写错的**：官方有**整套 VIP 转化流程**（见下 §5.x）。且 fixtures 的 `roomVipAbGroup`（`huiyuan_ListenTogether_TSpop` 等）显示**网易自己还在 A/B 调这件事** | **权益不共享，这一点无法缓解**。**UI 必须提前说明**，不能让用户以为是 bug |
| **eapi 加密参数会过期** | 已实测：公开容器因参数过期导致一起听全部 400 | eapi 得我们自己维护；这是 v1 §13.1 同一条风险的又一次现身 |
| **一起听可被风控单独剥夺** | 有黑猫投诉实例。**但找不到任何「一起听导致封号」的报告**（明确标注 [未找到]） | 用户可见的降级提示；不自动重试到被封 |
| **对方账号** | 网易云后端**要操作对方的账号关系**（邀请/接受是账号级行为） | **会话建立前明确告知**；不自动加入任何房间 |
| **NIM 是私有通道** | 想复现真实下行要带 `libnim`。**我们不做**——那等于重实现一个 IM 客户端 | 网易云后端定位为**轮询快照的降级模式** |
| **人数上限不可知** | 服务端策略，不在协议里 | UI 不承诺 |
| **同步阈值无依据** | 0.35s 来自单一实现（MeloX），不是规范 | 做成可配参数，实测调 |

## 9. 未定项

| # | 未定项 | 为什么重要 |
|---|---|---|
| 1 | **网易云后端能否可靠建房** | 决定它是否只能「被邀请」。两个来源矛盾，**必须实测** |
| 2 | **`sync/playlist/get` 要不要带 `playlistParam`** | 两个来源矛盾，**必须实测** |
| 3 | **控制权模型** | 双人 vs 多人是否不同？专利提到「共识切歌」（CN114979083A）、`commandType` 里有 `REPLACE`/`PLAYMODE_CHANGE`——**但控制权归谁、能否夺权，未核实** |
| 4 | **队列里遇到「对方取不到的歌」怎么办** | 官方行为是「跳过」。我们要不要提示、要不要提前过滤？ |
| 5 | **P2P 后端的房间模型** | 持久容器？成员管理？复用网格的配对还是独立一套？ |
| 6 | **聊天** | 官方有文本/表情/语音，且**解锁制**（`unlockChatNeededMs`）。v1 做不做？P2P 后端要不要自己做？ |
| 7 | **时钟同步的具体协议**（P2P 后端） | 需要选一个：粗略的 NTP 式对表，还是更简单的「锚点 + 单调钟外推」 |
| 8 | **本地音乐** | P2P 后端能用本地文件，但「对方没有这个文件」时的降级路径未定 |
| 9 | 与 v1 音质档位的关系 | 一起听时用哪一档？跟随谁的设置？（设计文档 §4.5 的两根轴在这里第一次交叉） |

## 10. 落地顺序（建议）

**不排里程碑**——本设计的未定项太多，先收敛再排。

一个初步直觉：

```
1. 实测未定项 1、2（网易云建房可靠性 / playlistParam）—— 成本低，决定整个后端形态
2. P2P 后端的时钟同步原型（与网格的 M2-M4 可并行）
3. 网易云后端（被邀请方 + 轮询快照）
4. UI：能力声明驱动降级
```
